# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Kneel is a Unity game project (Unity **6000.6.0f1**, URP 17, new Input System only: `activeInputHandler: 1`). There is no CLI build, lint or test pipeline. Building, running, and testing all happen in the Unity Editor. `com.unity.test-framework` is installed, but the project has no tests or `.asmdef` files yet, so all game code compiles into `Assembly-CSharp`.

Unity MCP (`com.coplaydev.unity-mcp`) is in `Packages/manifest.json`. When the Editor is open with it running, use it to inspect scenes, prefabs, and the console, and to trigger recompiles, rather than hand-editing Unity YAML. The package serves HTTP at `http://127.0.0.1:8080/mcp`. Register it with `claude mcp add --scope local --transport http unityMCP http://127.0.0.1:8080/mcp`. Only the `core` tool group is on by default. `manage_animation` needs `manage_tools(action="activate", group="animation")` each session, or enabling it in the Unity MCP window. Blend-tree child positions aren't exposed by `manage_animation`; set them with `execute_code` and `UnityEditor.Animations`.

Simulated input through `InputSystem.QueueStateEvent` is unreliable while the Editor is unfocused: events arrive late and get routed to the Editor. (For UI tests, sending `ExecuteEvents.moveHandler` / `submitHandler` to the selected object works; queued key presses get through with `InputSystem.settings.editorInputBehaviorInPlayMode = AllDeviceInputAlwaysGoesToGameView` and `backgroundBehavior = IgnoreFocus`, set in memory only and restored afterwards.) To script Play-mode tests:
- Set `Application.runInBackground = true`.
- Disable each component's `controls`.
- From an `EditorApplication.update` callback, write the cached input fields by reflection (`moveInput`, `sprintHeld`, `aimInput`, `blockHeld`), or invoke the handlers (`PlayerCombat.OnDrawPressed/OnStrikePressed/OnBlockPressed`).
- Time the test with `Time.unscaledTime`, because hit-stop changes `Time.timeScale`.

Other MCP gotchas:
- After adding a new `.cs` file, refresh with `mode: force` and check `read_console` for errors. A non-forced refresh can skip the import, and the next Play mode silently fails to start.
- `execute_code` blocks `AssetDatabase.DeleteAsset`.
- URP's material validation copies `_BaseMap` into the legacy `_MainTex` slot when a material loads. If a third-party material suddenly shows up as modified with only a `_MainTex` change, that's this, and it's safe to commit (as was done for `PolyKnights_Mat_01` and `PolygonPrototype_Texture_01`).
- About 18 Synty materials (PolygonPrototype `*_Global_Grid_*`, `*_Glass_*`, FX, and PolygonStarter/City sky and steam) still use Synty's custom or Built-in legacy shaders and the pre-2018 file format. They aren't URP-ready and will render magenta if used; convert them before relying on them.
- Movement bugs can depend on frame rate: builds run uncapped (vSync is off), and hit-stop shrinks `deltaTime` 20×. Reproduce high-fps behaviour in Play mode with `Time.captureFramerate = N` (reset to 0 after). The player's `CharacterController.minMoveDistance` must stay 0: at 0.001, the tiny steps of walking from rest at ≥300 fps were dropped, and the wall clamp then pinned the player at 0.1 m/s until they jumped.
- If Play-mode timings look stretched, check `Time.unscaledDeltaTime`. The Editor sometimes drops to about 1 fps, and gameplay `deltaTime` then caps at 0.33, which makes the results meaningless.

## Design docs

The team's Obsidian vault is a sibling folder, `../Obsidian`. The source of truth for design:
- `10-TenPager/*.tex`: the LaTeX ten-pager. `03Character.tex` has the **controls table**. Bind new verbs to the key it specifies.
- `02-Design/Mechanics/*.md`: per-mechanic feel targets (Combat Roll, Parry, Poise & Stagger).
- `04-Tech/Combat Feel Spec.md`: impact stack, and the rule that committed actions can't be cancelled but inputs are buffered.

The code currently diverges from the ten-pager in a few places:
- Sprint is on Shift, which the ten-pager reserves for the Ash ability, and it specifies "no walk/run toggle".
- Jump (Space) and Draw (R) aren't in its table.
- Parry triggers on the block *press*, while its prose says "time the release" (its table says "tap").

## Player architecture

The player is `Assets/Kneel/Player/Player.prefab`: a `CharacterController`, `PlayerMovement`, and a child Animator driven by `AC_Player.controller`.

- **Body**: the `EmberWarden` child is `Models/EmberWarden/Player_EmberWarden.fbx`, a Meshy mesh rigged in Blender with the Knight's bone names (`Hips`, `Spine_01..03`, `Hand_R`, …, right fingers with the `_1` suffix). It's Humanoid with its own avatar.
  - The mesh is in an A-pose, so the importer's `humanDescription.skeleton` was set to a T-pose. Re-importing with "Create From This Model" defaults loses that, and arms then retarget at an angle.
  - The instance is scaled ×1.037 so its `Animator.humanScale` matches the Knight's. The clip speeds and timings below were measured on the Knight, so they stay valid.
  - The body and the `Scabbard` (on `Spine_03`, across the back) render on rendering layers Default + Characters, like the level overrides expect.
  - The cape is skinned to 5 chains of 5 bones, `Cape_<column>_<segment>` under `Spine_03`. The top of the cape blends into the spine, so it stays attached at the shoulders. These bones aren't humanoid, so clips never move them.
  - After re-exporting the FBX, rebuild `humanDescription.skeleton` from every transform in the model, T-posing the arms. New bones missing from it break the avatar.
  - Its skin weights were cleaned in Blender with `Editor/Blender/ember_warden_fix_weights.py`: a headless FBX round trip, checked bone for bone against the original. It applied three rules:
    - No vertex mixes cape and arm bones. The back of the left upper arm jiggled with the cloth sim.
    - The hood is off the upper arms. Raising an arm squeezed the head.
    - Cape-weighted patches outside the cape body take the nearest clean weights. A patch at the back of the left elbow stayed behind with the cloth, so the arm looked split in two.
    - The pauldrons' undersides follow the arms. A cape-weighted vertex nearer clear arm skin (along the surface) than both the cape's cloth and clear body skin takes that arm skin's weights. The left pauldron's underside rode the cape's top corner and tore into spikes under it.
    - The head above the neck follows `Head`: from the neck bone to 5 cm above the head bone, within 22 cm of the neck-to-head line. The face and hood were 20-40% on the clavicles, neck and chest, so shrugs and arm raises warped them.
    - The rigged `.blend` this FBX came from isn't in the repo and still has the old weights. Rerun the script on any new export from it (`blender -b --python … -- in.fbx out.fbx`) until it's repainted there. Run it once, on the fresh export only: the head rule isn't idempotent.
    - Then `Editor/Blender/ember_warden_rigid_pauldron.py` (same command line) makes the left pauldron one plate. Its front was a Clavicle_L/Shoulder_L mix while its back and top were on Neck/Spine_03, and the hood rule had pulled the crest by the hood onto Head, so any reach sheared it into spikes. Inside the pauldron (dome ellipsoid, crest box, and a lame shell round the top of the upper arm, minus the bare arm skin) weights now depend only on how far out across the shoulder a vertex is: crest 15% Shoulder_L, outer dome 85%, the rest Clavicle_L. The border is smoothed two edges wide. In a 4-pose stretch test the left shoulder's torn edges went from 61-137 to 13-62 (the untouched right shoulder is 41-54). Pre-fix FBX: `Backups/Player_EmberWarden_before_pauldron_fix.fbx`.
    - Repainting these in Blender is the proper fix; until then, run both scripts, in that order, on every fresh export. They are Blender scripts only; there is no Unity-side weight postprocessor.

- **Input**: `PlayerControls.inputactions` is the source of truth. `PlayerControls.cs` is **auto-generated** from it by the Input System ("Generate C# Class"). Never edit it by hand. Change the `.inputactions` asset and regenerate instead.
  - The `Character` map defines Movement, Aim (mouse screen position), Sprint, Jump, Zoom (scroll), Strike (LMB), HeavyAttack (Q), Draw (R), Block (RMB), Dodge (Ctrl), Heal (F), Interact (E), and Ash1-Ash5 (1-5).
  - The `Debug` map holds ToggleOverlay (F1).
  - Each script creates its own `new PlayerControls()`. Player rebinds (the menu's CONTROLS screen) are binding overrides saved in PlayerPrefs; `Core/Input/KeybindService` applies them to every `PlayerControls` instance the moment one of its maps is enabled, so scripts need no rebinding code. A new rebindable action needs a line in `ControlsPanel.Layout` (one list that scrolls inside a masked viewport); a move with no key of its own (shield bash = Block + Strike, air attack = Strike in the air) gets a display-only `Line.Info` under OTHER. On-screen prompts that name a key should use `KeybindService.KeyFor("Interact")` (as `PickupPrompt` does), never a hard-coded letter, so they follow rebinds. The pause menu disables every enabled `PlayerControls` action while open (`GameplayInput`), which fires their `canceled` callbacks, so cache input in `performed`/`canceled` handlers rather than assuming a release always arrives from the device.
- **Tuning lives in ScriptableObjects** in `Assets/Kneel/Player/Settings/`: `PlayerMovementSettings.asset`, `PlayerCameraSettings.asset`, `PlayerCombatSettings.asset`, `PlayerLanternSettings.asset` and `PlayerCapeSettings.asset`. Scripts read them every frame, so edits apply live. `DebugTuningOverlay` (F1, on the `Debug` object in `Arena_S`) has sliders that write into those assets, so values tuned in Play mode persist. Add a slider there when adding a tuning field. It adds itself to every scene with a player (editor and development builds). Its **Enemies** section places enemies: pick a type, click the ground (snapped to that type's NavMesh, facing the player; right-click cancels), and it spawns frozen (`Enemy.Frozen`: no state updates, hits ignored, patrol ring dropped) until "Unfreeze all spawned". The types are `Enemies/Resources/EnemySpawnRoster.asset`; add a new enemy's prefab there, and check `Frozen` in its `Update` and `TakeHit` like the others.
- **`PlayerMovement.cs`** owns all player logic in `Update()`. Input callbacks only cache values. Each frame it:
  1. Aims: raycasts the mouse against `aimLayerMask` and moves the `aim` dot to the hit point.
  2. Resolves sprint (no stamina; sprint is unlimited).
  3. Rotates at a capped turn rate: toward the aim point when walking, toward the move direction when sprinting.
  4. Moves planar velocity toward the target with accel/decel, and applies gravity and jump (`sqrt(2gh)`).
  5. Moves via `CharacterController.Move` (no Rigidbody, no root motion).
  6. Feeds the animator.

  Walk speed depends on direction relative to facing, interpolated by angle across 5 speeds. The speed fields hold the clips' measured speeds, and `walkSpeedMultiplier` / `sprintSpeedMultiplier` scale them. The sprint steers speed and direction separately: speed builds with the accel rates and drops when facing and input disagree (turning bleeds speed), while the travel direction swings to the facing at `sprintGrip` °/s, so the run follows the body instead of sliding through turns.
- **Animator contract**: the code sets `xVelocity` and `zVelocity` to the **actual local planar velocity in m/s divided by `LocomotionSpeed`**, plus `LocomotionSpeed` (the `Locomotion` state's speed multiplier: 1 at rest, ramping to the walk multiplier at full walk speed in the current direction, then to the sprint multiplier at full sprint), `IsGrounded` (bool) and `Jump` (trigger). So the tree always sees the clips' own speeds, and the clips play faster to match the faster movement.
  - The `Locomotion` state is a Freeform Directional 2D tree whose child positions are each clip's real travel speed on the Knight. That is what keeps the feet from sliding.
  - If you add a clip or change a movement speed default, place the clip at its measured speed and keep the `PlayerMovementSettings` defaults in sync.
  - Renaming parameters means updating the string literals in `PlayerMovement.cs`.
- **`PlayerCamera.cs`** (on Main Camera) is an angled top-down follow camera in `LateUpdate`. It reads only `Zoom` (edge panning was removed). It finds the player through `PlayerMovement` if `target` is unset. `AddShake()` is used for impacts.
  - **Boss framing** (`SetFraming(subject, maxDistance)` / `ClearFraming()`, the Master's fight): the camera backs off only as far as it must to hold the boss, head to foot, and Kael inside the frame's middle 84%, biased 65/35 toward Kael (`framingBias`), up to the cap (13 m in Phase 1, 17 m in Phase 2). Kael's size is the screen box of a 0.9 × 1.8 m capsule, at least `framingMinPlayerPixels` (60) at 1080p, and the floor `framingPlayerRoom` (3 m) round him always stays in frame (room to aim). When the cap can't hold both, it leans toward Kael (at most `framingAcross` of the way) and lets the boss's head graze the top before it gives up Kael's room.
- **`PlayerCombat.cs`** is a code-driven state machine: `Sheathed → Drawing → Armed ⇄ Attacking / HitStun / Dodging → Sheathing`, with blocking as a flag while Armed. It runs before `PlayerMovement` (`[DefaultExecutionOrder(-10)]`).
  - The combo is two slashes (`Slash1` = `slash-1`, `Slash2` = `slash-3`). The pommel strike `attack-4` was dropped.
  - **Dodge roll** (base-layer `Dodge` state, trimmed `Stand To Roll` clip, frames 33–117, sped up to `dodgeDuration`):
    - Moves by code: `PlayerMovement.forcedVelocity` follows `dodgeTravelCurve`, which was measured from the clip's root motion so the body stays in sync.
    - Only starts from Sheathed/Armed; a roll pressed during another action is buffered (`dodgeBufferTime`).
    - Invulnerable between `dodgeInvulnerableStart/End`.
    - Stops short on a head-on wall hit (less than half the intended step got through).
    - Optionally rolls through enemies, via `Physics.IgnoreLayerCollision(Player, Enemy)`.
  - It doesn't use animator transitions or animation events. It `CrossFadeInFixedTime`s states on two layers and sets their weights itself:
    - `UpperBody`, masked by `AM_UpperBody.mask` (arms and head): ArmedIdle, Draw1/2, Sheath1/2, Block, BlockHit, Parry.
    - `FullBody`: Slash1, Slash2, HitReact, GuardBreak, Death.
  - **Draw and sheathe** are authored clips, not IK: `Animations/BackDraw/BackDraw.anim` (1.1 s, in `Draw1`, then `ArmedIdle`) and `BackSheath.anim` (1.2 s, in `Sheath1`, which holds its last frame while the layer fades out). They draw from the back in the classic fantasy style; the sword and shield come off together.
    - Carry: the scabbard is on `Spine_03`, diagonal across the back, mouth over the right shoulder blade, tip at the left hip; the shield sits over it (its `Socket_ShieldBack` moved 10 cm out so the board clears the scabbard; only its grip passes through, hidden). Both from `Kneel/Animation/Apply Back Carry Layout` (`Editor/BackDrawClipBuilder.cs`, reading `Animations/BackDraw/back_layout.json`).

## Level transitions

The four seams L1→L2→L3→L4→L5 (`Kneel/Core/Transitions/`, namespace `Kneel.Core`). One flow, `LevelTransition`, driven by `LevelCatalog.NextOf` (what comes next) and each scene's authored parts. Splash, menus, New Game and the L5 ending don't use it; Levels-menu jumps, Continue and death reloads use `SceneLoader`'s plain fade.
- **Phases**: a `PreloadTrigger` starts `SceneLoader.BeginPreload` (the next level waits at 90%, background loading held at Low). The `LevelExit` trigger is the threshold: input suspended, buffered presses dropped, `timeScale` 1, Kael shielded and invincible, enemies can't target him (`Enemy.PlayerInAgressionRange`), pause / F1 / F2 blocked, cursor and aim ember hidden. Outro: he sheathes and walks the exit's `walkPath` through `PlayerMovement.scriptedMove` (his own locomotion and animator, so no foot slide), a `LevelDoor` beat first if the exit has one, while the camera runs the exit's `CameraKey`s through `PlayerCamera.SetOverride`, the grade leans toward the next level (`TransitionGrade`: the next level's own global profile on a priority-100 volume, plus its fog and ambient) and Music fades (`SettingsRuntime.SetGains`). Loading: black, the save, `LoadingScreen` (art + line, at least `minLoadingScreen`), activation behind the art, settle (Kael placed at the `LevelArrival.start` before any `Start`, carried state applied after, warm frames on the intro's first shot, steady frame times). Intro: the arrival's keys, a lean back toward the previous level, sound fading in, the walk to the spawn, then control returns once; the lean, sound and a door closing behind him finish on their own after that.
- **Scene parts** live under each level's `_Transition` root, built by `Editor/Transitions/SeamBuilders.cs` (`Kneel/Transitions/Build Seam n`) and `SeamGlimpses.cs` (`Kneel/Transitions/Glimpses/...`), each rebuilding only its own group. Glimpses copy the neighbour's real pieces (`SeamCopy.Copy`: visual-only clones mapped through the seam frames, clipped to a box) and its far landmarks as `Kneel/Silhouette` meshes (combined). In-place edits they make: L1's road-end cart, bushes and sign moved, its backdrop bell house, neighbour house and twisted tree moved off the road, the exit's red fire glow and haze switched off, and two boundary boxes opened at the threshold; L2's tall burning house (Lot 57, with its lot) moved 9 m north-west so the start square opens west onto the road from L1, the debris on that edge moved aside, the start ring's west boundary walls (Wall_646-650) opened for the walk-in and closed behind him (a `LevelDoor` with no leaves), and the exit's boundary walls (Wall_791-793) opened at the threshold; L3's lane-mouth wall (2 segments) and causeway-end wall (2 segments) switched off, with unseen floors and blockers; L4's farm-track south wall opened (2 segments) for a field gate (`_Transition/FieldGate`, two fence leaves that swing shut behind him) and the hay wagon drawn up along the west wall; L4's portal bake swapped for a copy without its baked-in door, its throne-hall shell for a copy with its south wall cut away behind the portal (both by triangle centre in the doorway); L5's outer door leaves made non-static, and its nave carpet (`L5PolishCarpet.LowerCarpet`) runs to just inside the doors.
- **Roads** (owner: natural, blended into the existing ground): `SeamRoads.Paint` paints them into each level's own ground layout (`L1_Ground_Layout.png`, `L2_Ground_Layout.png`) in the colour of the level's own paths, the width wandering and the edges feathered; the road lists are `SeamBuilders.RoadsL1` / `RoadsL2`. It always starts from the untouched layout kept in `Editor/Transitions/LayoutSources~/` (not imported by Unity), so reruns don't build up; if a level's ground is ever repainted by its own tool, delete that copy and rerun the seam. L1's far ground (a plain plane) takes the road on as a ribbon of its own material (`SeamRoads.Ribbon`), and L3's lane floor runs on south of its mouth as a mesh in its own material and UV mapping (`SeamGlimpses.LaneFloorSouth`). Gates: L3's lane mouth (`_Transition/MouthGate`) and L4's farm track (`_Transition/FieldGate`) are farm-fence `LevelDoor`s, open as he arrives and shut behind him.
- **Copies** keep only the vertices their clipped triangles use (`SeamCopy.Compact`; silhouettes keep positions only, welded), so `Meshes/Transitions` stays small; delete orphans there after rebuilding (anything no level scene depends on). They skip renderers the source level has switched off (L5's blockout floor lies under its nave floor; copied, the two flickered), and the L5 nave glimpse sits 3 cm above L5's heights (`GlimpseLift`), clear of L4's own floor slab.
- **Intro cameras** start behind Kael looking ahead into the new level: L3 and L4 have no ground or sky worth seeing behind their starts. `SeamMap.Draw` prints an ASCII walkability map (colliders at body height) and `SeamMap.Top` a flat-lit overhead capture, for authoring walks.
- **Data**: `Core/Transitions/Resources/LevelTransitionSettings.asset` (timings, leans; F1 "Transitions" section) and `LevelTransitions.asset` (per seam: loading art, `artIsPlaceholder`, the line; per level: its look). Art: `UI/Art/Loading/LoadingArt_L<n>_<Name>.png`, 2560 × 1440, label `Placeholder`; overwrite under the same name.
- **Carried state** (`CarriedState`, `ICarriedState` on `PlayerCombat` for health and `PlayerPotions`; `CarriedStates.Register` for anything off the player, Ash's hook) is saved as `SaveData.entry`: the state carried into `entry.scene`. Any load of that level from the save applies it (Continue, a death restart); a shrine rest updates it. Old saves load with `entry.valid` false. The pause menu's auto-save merges into the save (`SaveServices.Update`) instead of replacing it.
- **Shrines** (`Gameplay/Markers/ShrineRest`, on every shrine: `L1.Shrine`, `L2.Shrine`, `L3.ShrineA/B`, `L4.ShrineA/B`, `L5.ShrineB`, `L5.ShrineC`): "E to Rest" in reach; resting kneels Kael, heals him, sets the flag and `SaveData.lastShrine`, and updates the carried state. A reload of the level puts him at its respawn point (`respawnFacing` × `respawnOut`, checked clear of boundaries) only if it's the last shrine rested at. Only Shrine C has `refillPotions`. The L1/L2 rest is on the shrine landmark, not the empty `_Gameplay/Checkpoint_Shrine`.
- **Safety**: a load requested while a preload waits (death, Quit to Main Menu) discards the preload under the black: it is let through and its roots switched off before any `Start` (`SceneLoader.IsDiscarding`), then the asked-for scene loads.
- **Potions** (`PF_HealthPotion`): one at each level's start and at most two more, away from shrines and each other. The levels' designed heal props (`L2_Loot_Heal`, `L3/L4_Pickup_Consumable`) are visual only: a used spot has a `PF_HealthPotion` on it and the prop switched off; unused ones stay switched off.
- **Tests**: `Editor/Transitions/TransitionPlaytest` (Play mode in a level; `Begin("walk" | "continue" | "presses" | "held" | "sprint" | "air" | "roll" | "armed" | "hitstop" | "enemy" | "deathpreload" | "quitpreload")`, `Shots` for a filmstrip, `CaptureFramerate`, `Tones` for audible metering, off by default) writes `Temp/TransitionPlaytest_<scene>_<scenario>.txt` and saves to `Temp/TransitionTestSave.json`, never the real save. Screenshots cost ~120 ms a frame, so time runs without them. `SeamCopy.Preview` renders an exit's or arrival's keys in edit mode with Kael placed along the walk.

## Repo conventions

- Every asset needs its `.meta` file committed alongside it. Move or rename assets in Unity (or move the `.meta` along with them) so GUID references don't break.
- `.gitattributes` routes binary assets (`*.fbx`, `*.png`, etc.) through Git LFS and marks Unity YAML for `unityyamlmerge`. `git-lfs` must be installed locally for those rules to apply.
- Work happens on `task/<Name>` branches and merges into `main` through PRs. `CODEOWNERS` assigns everything to `@ClumsySword/Core`.
